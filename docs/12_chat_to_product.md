# 12 只靠聊天做出成品：模式、初衷卡、問題卡

服務 `PURPOSE.md` 初衷 8。不列入每輪必讀：建置時讀一次，談需求、開問題卡、寫工單時再讀。

Claude 版把要 PO 決定的事放在私人網頁和資料庫；DSH 沒有這些（對照見 `docs/11_dsh_operations.md`）。本版的待決只有兩部分：**`ask_user_question`**（在 GUI 跳出題目卡，PO 選答案）和**本機帳 `DIRECTOR/PO_PENDING.md`**（唯一的長期紀錄）。

## 規則

### 一、先選模式

1. 使用者貼完啟動提示詞，總監的**第一則回覆只問一題**：一般模式還是小白模式。用 `ask_user_question` 問，選項各附一句說明：
   - **一般模式**：會看到 effort、子代理、設定這類技術問題，由你決定。
   - **小白模式**：你只要說想做什麼、看起來對不對；技術的事總監照預設決定，做完告訴你。
   啟動提示詞已經寫明模式，就不再問。
   選了小白模式，**同一輪**就開始談需求：只做唯讀確認、在 repo 外寫最少狀態，問第一個需求問題；完整建置延到談完需求、開第一位 worker 前（`BOOTSTRAP`「小白快速路徑」）。一般模式維持原順序。
2. 記錄：第 3 步建好 `DIRECTOR/` 後，寫進 `director_work.json` 的 `"mode": "general"` 或 `"beginner"`，和 `DIRECTOR_OPERATING_RULES.md` 開頭；在 `DECISION_REGISTER.md` 登記成 PO 指示。使用者之後隨時能換模式，換了照樣登記。
3. 兩種模式的安全底線一樣：推送、公開、付費、刪除、帳號、影響其他專案的設定，都要使用者同意（`docs/08`）。小白模式只是把問法換成白話，例如「要把成品放到網路上讓別人看嗎？」，不是跳過。

### 二、小白模式改了哪些步驟

| BOOTSTRAP 步驟 | 一般模式 | 小白模式 |
|---|---|---|
| 3、4、7、8、10 建置 | 照順序做完才談需求 | 快速路徑：談完需求、開第一位 worker 前才做（第 7 步改成確認模型、effort、子代理名額與沙箱） |
| 6 待決帳 | 第一則回覆之前先用 `ask_user_question` 問模式，題目同時記進 `PO_PENDING.md` | 同左，問法用白話；PO 不想用問題卡就在聊天問，總監照樣記進 `PO_PENDING.md`（`docs/11`） |
| 9 無關設定 | 列清單問 | 不問；DSH 沒有專案級外掛開關，本版不移植，什麼都不關 |
| 12 工作線編制 | 草案問 PO | 總監照 `docs/05` 定第一批（通常一條 worker 線），登記 DD，寫進初衷卡「由總監決定的事」；開子代理的同意併進「卡片對，請開助手」那一句，不另外問 |
| 13 第一份回報 | 六點，含技術數字 | 三句白話：準備好了、接下來要聊需求、有什麼要你點頭的；技術細節只寫在檔案；快速路徑下併進那一則 |
| 每次問問題 | 可以問技術問題 | 只問「要做什麼、像什麼、好不好、可不可以」；問不出白話的，總監自己決定並登記 DD |

### 三、談需求，寫專案初衷卡

1. 開工前一定先有 `DIRECTOR/BRIEF.md`（`templates/BRIEF.md`），兩種模式都一樣。已有 `LOCKED` 的卡就跳過這一節。
2. 一次問一到三題，用使用者的話，從大到小：做給誰、要做出什麼、一定要有的、絕對不要的、做完長怎樣。問法用 `ask_user_question`（一次可問多題）或在聊天問都可以；小白快速路徑的第一題固定是「這是給誰用的？第一版讓他做成哪一件事就有用？」。使用者說不清楚時，給兩三個具體例子讓他挑，不要用術語追問。
3. 談到表裡每一列都填得出來，就把整張卡用白話貼給使用者看，問「這樣對嗎？」。使用者說對，才把狀態改成 `LOCKED`、記下時間（讀系統時鐘）、在 `DECISION_REGISTER.md` 登記。沒說對之前不派任何工單。要同時問開工，照下面第 6 點。
4. **鎖定後只有使用者能改。** 總監發現需要改（做不到、互相矛盾、使用者後來說的話跟卡不一樣），用 `ask_user_question` 開一題問，不自己改。改了版次 +1，再請使用者確認一次。
5. 卡就是 `DIRECTOR/BRIEF.md` 這一份，鎖定後沒有鏡像、沒有網頁；要讓 PO 再看，把摘要貼回聊天（或 `present` 這張卡，但檔案卡要等這一輪結束才出現，不是即時畫面）。
6. **一句回覆同時確認卡和授權開工**（兩種模式都適用）。把卡和開工說明放在同一則貼出，說清楚：第一批做到哪裡就交給你看、開幾位 AI 助手（子代理，名字 `w1`、`w2`…）、effort、會用 DeepSeek Harness 帳號多少 token 與額外費用（沒有額外付費的服務就寫 0 元；時間只是估計就標「估計」；讀不到用量就說不知道，要量用量照 `docs/11` 跑 `dsh_usage.py`）、會新增或修改哪些檔案、會動哪份工作副本、公開、上傳專案內容、付費要另外問。本版所有子代理共用同一個工作副本，不是各自隔離的 worktree（`docs/11`）。貼卡前只備好首批工單草稿；鎖卡後、開第一位 worker 前，才跑 `gate_check --order` 和追溯核對（小白快速路徑此時 `tools/` 還沒建）；Strict 的規格審查要在貼出前做完（`docs/11`、`docs/02`）。同一筆待決項（`templates/PO_PENDING.md`）記下卡的版次、首批工單的版次與雜湊、工作線與範圍；收到回覆後把原文貼進 `ANSWER`。

   確認方式有兩種，同一輪做完：使用者直接回一句話（例如「卡片對，請開一位助手做這一批」），或總監用 `ask_user_question` 問兩題——「卡片對嗎？」（對／要改，哪裡要改用自訂答案寫）和「現在開第一批嗎？」（現在開／先不要）。兩題可以放同一次呼叫，但不要混成一題。DSH 沒有「提案卡」可以代替 PO 的同意，也沒有平台層的 user_asked 檢查：**開工授權是規則，不是平台擋**，總監自己要看清楚回覆再開。回覆照下表判讀，兩個決定仍分別登記在 `DECISION_REGISTER.md`：

   | 使用者回覆 | 狀態 | 總監做什麼 |
   |---|---|---|
   | 只說卡對（沒說開工），或「卡片對嗎」答對但開工題沒答 | `LOCK_ONLY` | 鎖卡；開工之後另問 |
   | 卡還是草稿，只說「開工」 | `NO_START` | 不開線；回「卡還沒確認，這樣對嗎？」 |
   | 明確說卡對、而且要開一位助手（或兩題都答對＋開） | `LOCK_AND_USER_ASKED` | 依序：記錄同意並鎖卡 → 核對範圍和工單雜湊跟貼出的一致 → 建 `tools/`，跑 `gate_check --order` 和追溯核對 → 做完開線前準備（`BOOTSTRAP` 第 7 步）→ 寫 `DISPATCH` 進 `DIRECTOR_LOG.md` → **同一輪**用 `subagent` 把第一批開完 → `list_agents()` 確認 |
   | 只回「收到」「好」，沒指明 | `NO_START` | 當作還沒答，換一句白話再問一次（可以用 `ask_user_question`） |
   | 被排程或 worker 完成通知叫醒的那一輪 | `NO_START` | 不得開新線；只能把待決帳的題目準備好，等 PO 回。本版沒有提案卡這回事 |
   | 核准後範圍或工單雜湊變了 | `NO_START` | 重新貼出說明，再問一次 |
   | Strict 規格審查沒做完 | `NO_START` | 先審完再貼 |

   範本（以店員班表為例）：

   > 我把第一版整理成這張卡。它是給店員上班前看的。打開後按一下「今天」，就能看到今天的範例班表。用測試資料，先做到這個流程能用。顏色等你看到畫面再選。
   >
   > 如果你同意，我會開一位 AI 助手（子代理）做這一批，再做一次獨立檢查。會用你 DeepSeek Harness 帳號的 token 用量，沒有額外付費的服務；約 20 分鐘是估計，做到可以查看第一版就先交給你。
   >
   > 我會在專案的本機工作副本新增 `index.html`，並在專案外加 `DIRECTOR/` 放工單和檢查紀錄；專案資料夾裡只會動這些檔。本版所有子代理共用這份工作副本，沒有各自隔離的 worktree。公開、上傳專案內容或付費各自需要另外同意。
   >
   > 如果卡片對，而且你要我現在開工，回「**卡片對，請開一位助手做這一批**」就可以；想先改內容，直接說哪裡要改，也可以回答下面兩題。

7. **卡可以只鎖第一階段。** `templates/BRIEF.md` 有選填的「第一階段」：B 表只填這一階段已確認的使用者、核心動作、限制和可觀察的驗收；一開始就會影響能不能用的要求（無障礙、品牌）照常列 B。配色、字型、版面這類看過才知道的事，放在卡上的「待預覽」，**不編 B 號**：`trace_report.py` 把表格每列第一欄的編號都當待做需求，編成 B-6 會一直列在「沒有工單的需求」。第一個預覽先走成品檢查（`docs/07`），讓使用者實際完成核心動作；有了真實畫面（至少兩種）才開問題卡，連回既有的 B 號。選擇若會改到已鎖的 B 項，照第 4 點重開確認、版次 +1。
8. **追溯指令**：派工前、每個 gate 前，卡和決策登記表一起查：

   ```text
   python -I -X utf8 <WS>/DIRECTOR/tools/trace_report.py --orders <WS>/DIRECTOR/orders --reports <報告資料夾> --decisions <WS>/DIRECTOR/BRIEF.md --decisions <WS>/DIRECTOR/DECISION_REGISTER.md
   ```

   舊專案還沒有 `DECISION_REGISTER.md` 才只給 `BRIEF.md` 一個，結果和以前相同。「沒有工單的需求」只有 B 開頭的列算待排項目；DD、PO、OD 的列只是決策紀錄，列出來不代表缺工單。「TRACES_TO 找不到的編號」有東西，是工單對到不存在的編號，改工單。

### 四、要使用者選的事：問題卡與本機待決帳

適用：中途有兩個以上做法、使用者看了才能決定的事，例如 A 風格或 B 風格、版面、配色、角色長相。不適用：純技術選擇（總監自己決定）、要使用者動手的事（照 `docs/03` 的 PO 動作項）。

做法只有兩部分：

- **`ask_user_question`**：在 GUI 跳出題目卡。一次呼叫可以問一到三題（工作慣例，不是平台的硬限制；`docs/11`）；每題有選項（標籤＋一句說明），可勾多選（`multi_select`），也可以不選選項、用自訂文字回答。總監問了就**阻塞等答案**，PO 回答前這一輪不會往下走。只有總監（root session 的 runtime root）能呼叫；worker 是子代理，呼叫會被拒，有問題一律回報總監。PO 跳過某一題時，回傳是「沒有選項、也沒有自訂答案」，代表**還沒答**，不是同意。
- **`DIRECTOR/PO_PENDING.md`**：本機帳，長期紀錄與唯一來源。每題照 `templates/PO_PENDING.md` 記 `ID / STATUS / QUESTION / QUESTION_TOOL / OPTIONS / RECOMMENDED / IMAGES / SOURCE / ANSWER / RESOLUTION`。

Claude 版用私人網頁、版本快照、本機資料庫、冪等鍵、收條和留言叫醒來做這件事；DSH 都沒有，本版不移植（`DEEPSEEK-PORT.md`）。以下用問題卡和本機帳做到同樣的事。

1. **開題前先記帳**：在 `PO_PENDING.md` 的「未關閉」新增一筆，欄位照範本：`ID`（`CH-01`，或沿用 `OD-xx`）、`CREATED`、`STATUS: open`、`QUESTION`（一句話）、`QUESTION_TOOL`（用 `ask_user_question` 問的題號或一句話；只在聊天問的寫 `NONE`）、`OPTIONS`（A／B／C，各一句影響）、`RECOMMENDED`（建議＋一句理由）、`IMAGES`（要 PO 看的截圖路徑；同一個視角的前後對照放一起並標明方案；沒有寫 `NONE`）、`SOURCE: NONE`（收到回覆才改成 `ask_user_question` 或 `聊天`）、`ANSWER`（先留空）、`RESOLUTION`。每題都要對到初衷卡的 B 編號，題目或 `RECOMMENDED` 裡寫 `B-2`；對不到卡上任何一條的題目不要開，先回頭問要不要改卡。例外：第一輪的模式題 `CH-00` 在卡之前，沒有 B 編號。
2. **一題只問一件事；選項最多四個。** 每個選項寫「選了會怎樣」，不要把兩件事包成一題。總監的建議放第一個，標籤照工具建議加「（推薦）」（`label` 加 `(Recommended)`，或中文「（推薦）」），`RECOMMENDED` 欄也寫同一句理由。
3. **看圖的題目先給圖。** 先把真實成品的截圖放在**同一則訊息**，用 markdown 圖（例：`![A：明亮版](<路徑>)`、`![B：沉穩版](<路徑>)`）。PO 端會不會直接顯示還沒實測（NOT_VERIFIED），看不到就照實說，並把檔案路徑和一句說明寫在同一則，請 PO 直接開檔。`ask_user_question` 的選項只有文字和說明，不能夾圖，所以圖一定要在問之前給。`present` 的檔案卡要等這一輪結束才出現，**不能**用它代替「問之前先看圖」；`present` 一次放 1～2 個最重要的檔（上限 8 個），子代理做的成品要總監自己呼叫 `present` 才會出現。另外，`present` 的桌面預覽不支援把本機圖片內嵌（要 HTTP(S) 頁面），所以成品圖請走聊天 markdown 圖這條路。不要用示意圖假裝成品；還沒有真實畫面就先做預覽（`docs/07`），不要開純文字猜風格的題。
4. **問**：同一次 `ask_user_question` 放一到三題（工作慣例）；用 PO 的語言、不要用術語。要 PO 一次決定兩件事就放兩題，不要混成一題。PO 可以用自訂答案寫自己的話。
5. **收**：PO 在 GUI 答完或聊天回覆後，把原文貼進 `ANSWER`、`STATUS: answered`、記下時間（讀系統時鐘），`SOURCE` 寫 `ask_user_question` 或 `聊天`。同一題以**先落檔**的答案為準；晚到但不同的答案保留原文，問 PO 是不是改了主意，不直接覆蓋。PO 跳過（空答案）：`STATUS` 保持 `open`，不當成同意；不要同一輪原地重問，下一輪換句話再問一次；仍被跳過就照 `RECOMMENDED` 做不影響安全的部分並在 `RESOLUTION` 記明，涉及核准、推送、付費、刪除、公開的，跳過就是不能做，停下來等 PO。
6. **同輪處理**：答案收到後，同一輪處理完（照答案開工單、派工，或告訴 PO 會怎麼做），關掉時 `STATUS: closed`，`RESOLUTION` 寫處理結果和時間；不能當輪完成的寫續辦紀錄。決定本身登記進 `DECISION_REGISTER.md`。
7. **聊天只說一句**：「待決帳新增 CH-01，圖在上一則」，不在聊天重貼整題；要看圖的那一則訊息就是圖的所在，不能省。
8. **同一題同一版只派一張工單。** 問題卡派出的工單 `TRACES_TO` 寫到 B 編號，再加上題號和版（例如 `CH-01 r2`）；工單編號由總監自己編，同一題同一版固定用同一個編號。之後發現 PO 其實選了別的，先查帳和聊天原文，再重開一題，不偷偷改。
9. **選擇改到已鎖的 B 項**：照第三節第 4 點，先問 PO 要不要改卡；同意後版次 +1、狀態回 `DRAFT`，再確認一次。

### 五、不做歪的檢查

1. 每張工單的 `TRACES_TO` 寫它服務的 B 編號（可以和 DD、OD 並列）。問題卡派出的工單，另外寫上題號和版，例如 `CH-01 r2`。
2. 派工前、每個 gate 前跑：

   ```text
   python -I -X utf8 <WS>/DIRECTOR/tools/trace_report.py --orders <WS>/DIRECTOR/orders --reports <報告資料夾> --decisions <WS>/DIRECTOR/BRIEF.md --decisions <WS>/DIRECTOR/DECISION_REGISTER.md
   ```

   - 「TRACES_TO 找不到的編號」有東西：工單對到不存在的需求，改工單。
   - 「沒有工單的需求」有東西：還有沒做的需求，排進下一批，或問使用者是不是不要了。
3. 成品交件時，對著初衷卡每一列的「怎麼算做到」檢查，結果寫進 gate 報告；最後由使用者看成品說「對」。

### 六、待決不漏讀

待決帳和問題卡一樣不准漏讀（`docs/03`「PO 的訊息不漏讀」）。也不准重複做：同一題同一版只派一張工單。

1. **每輪第一步**：照 `docs/06`，唯讀收集時讀 `PO_PENDING.md` 的未關閉項目和聊天裡還沒處理的 PO 回答；`ask_user_question` 的回覆就在對話裡，連同原文一起看。處理完的同一輪改 `answered`／`closed` 並寫 `RESOLUTION`。
2. **沒有自動叫醒。** DSH 沒有留言叫醒、置頂頁、收條。`ask_user_question` 是阻塞的：總監問了，這一輪就停在等答案；PO 在聊天回話也會開始新的一輪。PO 一直沒答（或跳過）的題目，`STATUS` 保持 `open`，下一輪再問**一次**同一題（換句話或把選項縮小）；已回答的不再問，也不要每一輪重問同一題。
3. **叫醒的來源**：PO 在 GUI 回答、PO 在聊天說話、排程（只有 PO 明確要求才建，`docs/11`）、worker 完成通知。被排程或 worker 通知叫醒的那一輪，不得代替 PO 開新線或改卡（第三節第 6 點）。
4. **沒有收條、沒有逾時標記**：PO 不會在問題卡上看到「總監已讀」。處理晚了照實寫在 `RESOLUTION`：幾點才讀到、晚了多久。同一個答案重複出現（PO 重問、重貼）只處理一次，記一筆就好。
5. **每輪結束前自查**：`PO_PENDING.md` 沒有「已答卻沒關閉」的題；聊天裡的回答都記進帳；沒有重複開的題；本輪問過的題都有 `SOURCE` 和 `ANSWER`。有總管（選用角色）時，總管例行查一次「`answered` 超過 10 分鐘還沒 `closed`」的項目提醒總監；總管自己不能問 PO。
6. 處理 PO 的插話：同一輪先處理，再回原工作；會改變做法的，同一輪寫進 `DECISION_REGISTER.md` 和相關規則。

## 為什麼

- 使用者想做的東西會在對話裡慢慢變形：每一輪的小決定單看都合理，加起來卻偏離一開始想要的。把一開始的需求寫成使用者確認過、只有他能改的卡，每張工單都對回去，偏掉時馬上看得到。
- 風格這類選擇用文字很難描述，使用者看圖才知道要哪個。Claude 版放在獨立的私人頁面，使用者有空時點一下就好，也不會在對話裡被其他訊息沖掉。DSH 沒有私人頁面、置頂或留言叫醒，只能在對話裡用問題卡問：問題會佔掉一則訊息、只存在於對話中，PO 不答就不會前進；總監問了要等答案，沒答下一輪再問一次。這是限制不是設計，所以題目要短、圖要和題目同一則、一次不要問超過三題，並把題目和答案都留在 `PO_PENDING.md`，中斷或換對話也接得回來。
- 本機帳比 Claude 版的資料庫簡單：沒有自動去重、冪等鍵和大量狀態，代價是總監要自己確認同一題不重問、答案不漏記；好處是檔案讀得到、可備份、PO 隨時能翻。
- 不懂技術的人被問「要不要改這個設定」只會卡住。小白模式把這些交給總監的預設，使用者只回答自己真的能回答的事。DSH 沒有專案級外掛開關，這類問題本版不移植；技術選擇改由總監決定並登記 DD。
